# docs: 'Cache Key Generation' section understates hash inputs — silently causes hash drift between shared-cache consumers

## Metadata

- **GitHub Issue**: [#235](https://github.com/63Klabs/cache-data/issues/235)
- **Type**: documentation, Approved for Development
- **Assigned**: chadkluck
- **Created from issue**: 2026-10-03

## Description

### Summary

The "Cache Key Generation" paragraph in `docs/features/cache/README.md` describes the cache-key inputs more narrowly than what the code actually does. The JSDoc on `Cache.getIdHash` is accurate; the README paragraph is not. This tripped us up in production when two Lambdas configured to share a cache entry (via `sharedCacheId`) drifted on a single cache-profile field and, as a result, produced different `id_hash` values.

### The discrepancy

#### README (misleading)

`docs/features/cache/README.md` → "Cache Key Generation":

> Cache keys are generated by hashing the connection object (`host`, `path`, `parameters`, `headers`) along with the Lambda Application Identifer.

This implies only the `connection` object contributes to the hash (and only a subset of its fields at that).

#### JSDoc on `Cache.getIdHash` (accurate)

From `src/lib/dao-cache.js` (v1.3.16):

> Get the unique identifier hash for this cache entry. This hash is generated from the connection, data, and cache policy parameters and uniquely identifies this specific cache entry.

#### What the code actually does

In `CacheableDataAccess.getData` (`src/lib/dao-cache.js`, around line 3126):

```js
const idToHash = { data: data, connection: connection, cachePolicy: cachePolicy };
const cache = new Cache(idToHash, cachePolicy);
const idHash = cache.getIdHash();
```

The Cache constructor forwards the wrapped `{ data, connection, cachePolicy }` object to `Cache.generateIdHash`. That method deletes only `connection.options`; every remaining field, including every field of `cachePolicy`, flows into the hash:

```js
// generateIdHash (paraphrased)
if (clonedIdObject.connection?.options) { delete clonedIdObject.connection.options; }

if (this.#useToolsHash) {
  return tools.hashThisData(this.#idHashAlgorithm, clonedIdObject, { salt });
}
// object-hash path also hashes the entire cloned object
```

Both hashing backends (`object-hash` with `unorderedObjects/Sets/Arrays: true`, and the built-in `tools.hashThisData`) walk the entire object recursively. Nothing under `cachePolicy` is stripped.

So the effective hash input is:

- `data`
- `connection` (minus `connection.options`)
- `cachePolicy` (in full, including behavioral fields like `defaultExpirationInSeconds`, `defaultExpirationExtensionOnErrorInSeconds`, `expirationIsOnInterval`, `overrideOriginHeaderExpiration`, `encrypt`, `hostId`, `pathId`, `headersToRetain`, `profile`)
- The salt (`sharedCacheId` → `CACHE_SHARED_ID` env var → `AWS_LAMBDA_FUNCTION_NAME` → `""`)

The README's list of "`host`, `path`, `parameters`, `headers`" is a subset of `connection` fields and omits both `data` and `cachePolicy`.

### Why this matters (real-world impact)

We have two Lambdas that share the same cache entry via `sharedCacheId` — a writer (scheduled refresh) and a reader (API). Both point at the same `connection` object (`{ host: "internal", path: "org_index" }`) and both look up a cache profile named `org_index` on an `internal` connection. The profiles started out identical.

Later, we added `defaultExpirationExtensionOnErrorInSeconds: 30` to the reader's profile only (to shorten the error-TTL for a stale-503 recovery scenario). The writer's profile still didn't have that field.

Everything else was identical: same `sharedCacheId`, same DynamoDB table, same S3 bucket, same encryption key, same connection object.

Result: the two Lambdas silently began writing/reading different `id_hash` rows. The writer's data was correctly landing in DynamoDB, but the reader never saw it. From the reader's perspective the cache was permanently empty, and it kept falling through to its error-fetch path (a fallback we use to avoid direct origin calls), returning "no data available" to clients indefinitely.

Because the README paragraph reads as "the hash uses these fields of `connection`", it's easy to assume that a difference in cache profile fields doesn't affect the key. It does — and there's no diagnostic that surfaces the drift.

### Requested changes

**Documentation (the main ask):**

Update `docs/features/cache/README.md` → "Cache Key Generation" to match the JSDoc and the code. Suggested wording:

> The `id_hash` for a cache entry is derived from three inputs together with a salt:
>
> 1. The `data` parameter passed to `CacheableDataAccess.getData()`
> 2. The `connection` object (all fields except `connection.options`, which is intentionally excluded so runtime toggles like `forceRefresh` and `timeout` do not shift the key)
> 3. The full `cachePolicy` object — including behavioral fields such as `defaultExpirationInSeconds`, `defaultExpirationExtensionOnErrorInSeconds`, `expirationIsOnInterval`, `overrideOriginHeaderExpiration`, `encrypt`, `hostId`, `pathId`, `headersToRetain`, and `profile`.
>
> The salt is resolved from `sharedCacheId` → `CACHE_SHARED_ID` env var → `AWS_LAMBDA_FUNCTION_NAME` → `""`.
>
> **Consequence:** Two Lambdas that want to share a cache entry must use byte-identical `connection` (minus `options`) and `cachePolicy` objects in addition to the same `sharedCacheId`. Any drift in a cache-profile field — even a purely operational one like `defaultExpirationExtensionOnErrorInSeconds` — will produce a different `id_hash` and the functions will silently read/write different rows.

It would also help to add a short "Shared cache pitfalls" callout in the "Shared Cache" section pointing out this gotcha, since the current example there ("Two Lambda Functions Sharing Cache") shows both functions using the same inline cache profile, which sidesteps the drift risk that exists in real projects where each function defines its own `connections.js`.

**Optional follow-ups (worth considering, not blocking):**

1. Should behavioral cache-profile fields (error-TTL, interval flag, override flag) be part of the *identity* of a cache entry, or only govern how that entry is *served/expired*? Today they're part of identity because they flow into the hash. That means two consumers agreeing on "this is the same cached thing" have to also agree on every behavioral knob. A stricter identity — e.g., only `hostId`, `pathId`, `encrypt`, `profile` from `cachePolicy` — would be more forgiving and would let each consumer tune its own error/interval behavior without accidentally splitting the cache. This is a behavior change so it would need a major version, but it's worth thinking about.

2. Consider logging the computed `id_hash` (and maybe a short summary of the object that produced it) at debug level in `getData`, so hash drift is diagnosable without a code dive.

3. Minor: `Cache.init` gates on the env var `CACHE_DATA_USE_TOOLS_HASH` but reads `CACHE_DATA_USE_TOOLS_HASH_METHOD` (`src/lib/dao-cache.js` ~L1536). Setting `CACHE_DATA_USE_TOOLS_HASH_METHOD` alone therefore doesn't enable `useToolsHash`. Not related to the docs issue but adjacent enough to mention.

### Environment
