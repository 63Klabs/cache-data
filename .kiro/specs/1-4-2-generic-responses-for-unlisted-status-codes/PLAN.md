# Generic responses fall back to the 500 template for 201, 202, 204 and other unlisted status codes

> **Status**: Locked 2026-11-13
> **Issue**: [ISSUE.md](ISSUE.md)
> **Reviewed against**: `dev` at `125c03f` (package version 1.4.2) on 2026-11-13

## 1. Summary

The generic response modules (`jsonGenericResponse`, `htmlGenericResponse`, `xmlGenericResponse`, `rssGenericResponse`, `textGenericResponse`) hold templates for ten status codes. `response(n)` returns the 500 template for every other code, and `Response.reset()` (called by the constructor) copies that body onto a response that keeps the caller's status. A handler that builds `new Response(req, { statusCode: 201 })` or calls `reset({ statusCode: 202 })` sends a 2xx status with `{"message":"Internal Server Error"}`. Applications that always pass their own body are not affected.

The issue is accurate. Reading the code adds three things it does not say. First, an application that customizes `response500` through `Response.init()` currently sends its own 500 body on a 201, because the fallback is `this.response500` on the merged object. Second, the XML and RSS formatters branch on `statusCode === 200`, so a new 2xx template would render as `<error>Created</error>` unless the branch changes. Third, a `null`-body template for 204 only works on a fresh instance. On an existing instance `reset()` keeps the previous body because `set()` ignores falsy values.

Locked fix: add templates for 201, 202, 204, 409, 422, 429 and 503 to `STATUS_CODE_MAP` (Decision 1), give 204 a `null` body, make the XML and RSS formatters treat every 2xx as success, and make `reset()` assign `null` when the resolved body is `null` (Decision 3). Replace the single 500 fallback in `response(n)` with a fallback by status class (Decision 2): an unlisted 2xx uses the 200 template, a 4xx the 400 template, a 5xx the 500 template. A 1xx, 3xx or 205 gets a bodiless result (Decision 8). Keep `response427`, mark it deprecated, add 429 as its replacement, and log a one-time warning when `response()` resolves 427 (Decisions 4 and 9). Ship as a PATCH in 1.4.2 (Decision 5), recording the conflict with AGENTS.md 2.2 as an exception and leaving AGENTS.md unedited (Decision 10). Update the types, tests, documentation and CHANGELOG.

## 3. Current state

- **Factory.** `createGenericResponseModule(contentType, bodyFormatter)` (`generic.response.js:47-71`) loops over `STATUS_CODE_MAP`, builds `response<code> = { statusCode, headers, body: bodyFormatter(statusCode, message) }` with one shared `headers` object, and attaches `response(statusCode)`. `STATUS_CODE_MAP` is not exported; only the factory is.
- **Format modules.** JSON `{ message }`; text the message; HTML `<html><head><title>{code} {title or message}</title></head><body><p>{message}</p></body></html>` with title overrides for 200 ("OK") and 500 ("Error"); XML and RSS `<hello>` for 200 and `<error>` otherwise, with "418 " prepended for 418 (`generic.response.{json,text,html,xml,rss}.js`).
- **Only caller.** `Response.reset()` (`Response.class.js:205-222`) resolves a content type, takes `genericResponses.response(code)` for headers and body, and calls `set()`. The constructor calls `reset()` (`:104-107`).
- **Customization.** `Response.init()` merges application templates over the built-in module with a spread (`:142-170`). An application can already supply `response201` itself, and its value wins over any built-in, because the application's keys come last. `docs/01-advanced-implementation-for-web-service/response-management.md:165-187` documents `response404` and `response500` overrides.
- **History.** 1.3.10 centralized the factory without adding statuses (`aaa1cc6`, spec `1-3-10-clean-up-generic-responses`). Status 408, 418 and 427 were added one at a time (`86d7ee3` in 2024, `bc9d1d9` for 427). The pattern is to add a code when someone needs it, and the 500 fallback was never a design decision about unlisted codes.
- **Sibling work.** `Response.setBodyToNull()` shipped in 1.4.1. The 1.4.1 plan spun this issue off as S2 (Q5 of that plan). Two other 1.4.2 issues touch the same class: `Response.init()` merges `xmlResponses` into the HTML slot (`Response.class.js:163` assigns to `#htmlResponses`), and `setStatusCode()` and `setHeaders()` flip a non-JSON content type to JSON. Neither is needed here.
- **No unreleased section.** `CHANGELOG.md` starts at `v1.4.1 (2026-11-12)`. `package.json` is already 1.4.2, so this change needs a new `v1.4.2 (unreleased)` section (Decision 5).

## 4. Review

### 4.1 Security

- **Not a vulnerability, no disclosure handling needed.** The wrong body is a correctness and observability defect. Nothing attacker-controlled flows into the templates.
- **Template content stays static.** The HTML, XML and RSS formatters concatenate `message` into markup without escaping. That is safe only because the messages are constants in `STATUS_CODE_MAP`. New entries must stay constants. No template may take caller input, and none should echo a request value.
- **Redirects.** No 3xx template is added (Decision 1). The caller sets `Location` through `reset({ statusCode, headers })` (`Response.class.js:218`); no template may guess a location, which would be an open-redirect risk.
- **Information exposure.** Today an application with a custom `response500` returns that body, which may include an internal error code, on a 2xx or a 4xx. The change removes that for every status that now resolves to a 2xx or 4xx template. It is a correction, but it is a visible output change (N1, Risks).
- **Fail-closed behavior after Decision 2.** A status in 200-299 that has no template gets the 200 body, 400-499 the 400 body, 500-599 the 500 body. A value that is not a status (NaN, below 100, 600 and above) still gets the 500 body, so unknown input fails towards "something went wrong". A class fallback never turns an error status into a success body or the reverse. 1xx, 3xx and 205 get no body (Decision 8).
- **Content where HTTP forbids it.** RFC 9110 says a 204 and a 304 are terminated by the end of the header section and cannot contain content (sections 15.3.5 and 15.4.5), and a server MUST NOT generate content in a 205 (section 15.3.6). A 2xx class fallback to the 200 template would put `{"message":"Success"}` on a 205. That is why Decision 8 gives 205 no body.
- **Caching.** `finalize()` adds `Cache-Control: max-age` and `Expires` from `routeExpirationInSeconds` to every status below 400 unless the application sets them (`Response.class.js:742-753`). With real 201, 202 and 204 templates applications are more likely to send those statuses, and a cached 201 or 204 to a `POST` or `DELETE` may be unwanted. The sibling plan recorded this as S5 (note only). It stays out of scope; the documentation for the new templates points at `Cache-Control` the way `setBodyToNull()` does.

### 4.2 Software engineering

- **Backward compatibility (AGENTS.md 2.1).** What changes for an existing caller:
  - New exports `response201`, `response202`, `response204`, `response409`, `response422`, `response429`, `response503` on five modules, and the same members on `GenericResponseModule`. Each is permanent public surface.
  - `response(n)` and the `Response` constructor and `reset()` return a different body for every status that now resolves differently: the seven added codes (their own template), every other 2xx (200 template), every other 4xx (400 template), and no body for 100-199, 300-399 and 205. Before, all of them returned the 500 template. An application that read `response(201).statusCode` expecting 500 would change.
  - An application with a custom `response500` no longer sees it on those statuses (N1). A custom `response200` or `response400` now applies to every unlisted 2xx or 4xx respectively, which is new coupling (N2).
  - With Decision 3, a custom template with `body: null` clears the previous body on an existing instance. Today it keeps it.
  - Unchanged: every status that already has a template, 5xx statuses without a template, out-of-range input, and every call that supplies a body.
  - This is "changed default behavior" in AGENTS.md 2.2 terms, which that table classes as MAJOR. Decision 5 classes it as PATCH. Decision 10 records the exception.
- **Formatter branches.** XML and RSS need the `statusCode === 200` test replaced with a "2xx is success" test (C4). Every new 2xx code renders `<hello>{message}</hello>`, matching the 200 shape, and the existing outputs for 200 and every error code stay identical.
- **Null body in the factory.** The formatter interface is `(statusCode, message) => body`. A 204 needs no formatter call. A small private constant in `generic.response.js` lists the codes with no body (204 only, after Decision 1); the factory sets `body: null` for them and skips the formatter. The five format modules need no change for it. `STATUS_CODE_MAP` is private, so its shape can change, but a separate set avoids changing the map's value type.
- **Class fallback in `response()`.** `response(statusCode)` keeps its parse and direct lookup, then resolves a representative template by range. It must read `this.response200`, `this.response400` and `this.response500` rather than closed-over values, so an application's templates merged by `Response.init()` apply. It returns that template object unchanged, as it does for 500 today, so `response(410).statusCode` is 400 and `response(410) === response400`. Statuses 100-199, 300-399 and 205 return `this.response204`, so `response(301).body` is `null`. An application that customizes `response204` with a body changes what those statuses send. `Response.reset()` reads only `headers` and `body`, so the caller's status stays. Copying the object with the requested status was considered and rejected: it allocates per call and breaks the identity checks the existing tests use. The range checks run only after a direct lookup misses.
- **Where the `reset()` change lands.** `reset()` builds `newObj.body` and calls `set()`. One line after `this.set(...)`: if `newObj.body === null`, assign `this._body = null`. `set()` and `setBody()` stay unchanged, which keeps the 1.4.1 decision that falsy values passed to `setBody()` are ignored.
- **Deprecating `response427`.** AGENTS.md 2.1 asks for `@deprecated` with migration instructions, a logged warning when the deprecated feature is used, a CHANGELOG notice, and a migration path in the documentation. A property read cannot log. Two designs were checked against the code. A getter that logs fails because each format module builds its export with `{ ...mod, json }` and `Response.init()` merges with a spread; a spread reads every enumerable getter at load, and a non-enumerable one would be dropped by the spread, which would remove `response427` from the merged module. Logging inside `response()` when it resolves 427 works: `Response.reset()` calls `response()`, and `generic.response.js` can require `DebugAndLog.class` without a cycle (`DebugAndLog.class.js` requires only `./utils`, `./PowertoolsInit` and `../utils/LoggerBridge`). Decision 9 takes the second design, with a module-level flag so it logs once per container. `DebugAndLog.class.js:138` is a precedent for a deprecation message through `DebugAndLog.warn`.
- **Duplicated lists.** The status list exists in `generic.response.js`, in `types/lib/tools/index.d.ts`, in the factory JSDoc `@returns`, and in two test files. A test that compares the keys of all five modules with one shared list prevents drift.
- **Tests that change (C10).** `KNOWN_STATUS_CODES` in two files, the "all 10" test, `STATUS_CODE_MESSAGES`, the per-format `EXPECTED_OUTPUTS`, and Property 3, which asserts that any integer outside the known set returns `response500`. That property is replaced by one per class. The per-format `response(999)` tests stay valid because 999 is out of range.
- **Property tests (steering `test-execution-monitoring.md`).** Generators for the class properties are built from the class range (`fc.integer({ min: 400, max: 499 })`) with a filter that removes codes in the known list. The filter is a precondition on a constant held in the test, not the predicate under test (the predicate is which template the code resolves to), so the properties are not vacuous. Do not pass `seed` to `fc.assert`.
- **Documentation that is wrong today.** `docs/features/tools/README.md:1470-1540` ("Generic Response Generators") shows `jsonGenericResponse(200, {...})` and `htmlGenericResponse(200, html)` as functions. They are module objects, not callable (`generic.response.json.js:11` exports `{ ...mod, json }`). The section is rewritten (I1, confirmed in Decision 7).
- **Type updates.** `GenericResponseModule` lists each `responseNNN` member (`types/lib/tools/index.d.ts:2330-2356`). Adding required members is accurate for the shipped modules. It breaks only a consumer who hand-builds an object typed as `GenericResponseModule`. The `response()` description ("Falls back to response500 for unknown codes") must change to describe the class fallback.

### 4.3 Cloud engineering

- **Deployed topology.** No infrastructure change. The package is code only; no template, IAM, KMS, parameter or stack is touched. Rollout is a normal npm release and rollback is the previous version.
- **What each hop does to a 204.** API Gateway REST API (Regional and edge-optimized) removes the body and `Content-Type` of a 204 (observation O12 in `docs/cloudfront-notes/lambda-proxy-response-body.md`), and accepts `body: null` without a 502 (O9). Behind REST API the new 204 template is visible only in `toObject()`, `finalize()` output and logs. HTTP API, ALB and Lambda function URL were not tested (that document, line 58). Decision 6 is to state that limit in the documentation and not verify further.
- **205, 304 and other 3xx.** None of these was tested behind API Gateway or CloudFront. They return a `null` body (Decision 8), the shape O9 verified for 202 and 204 on REST API only, and the documentation says so.
- **Stages and config drift.** `routeExpirationInSeconds` and `errorExpirationInSeconds` are per-application settings. The new templates inherit the cache-header behavior in 4.1.
- **Cost, quotas, observability.** None. Templates are built at module load; seven more small objects per module add negligible memory and startup time. Class fallback adds one range check on a lookup miss. The `RESPONSE` log line already reports the status and body size, so a bodiless 204 logs 0 bytes. Decision 9 adds one `warn` line per container the first time `response()` resolves 427.
- **Runbook.** Operational note for the release: applications with a customized `response500` stop seeing that body on unlisted 2xx and 4xx statuses (N1). They can restore control with `response400` or `response200` customization (N2) or a custom `response<code>`.

## 5. Gaps and observations

1. **Fallback strategy** was undecided in the issue. Decision 2 chose a class fallback, and Decision 8 gives 1xx, 3xx and 205 no body.
2. **Custom `response500` coupling (N1).** The issue does not mention that an application's custom 500 is what unlisted codes get today, and that the change replaces it for 2xx and 4xx.
3. **XML and RSS success branch (C4).** The issue says each module "would need the new entries" but not that two formatters hard-code 200.
4. **`reset()` and `null` bodies (C6).** The issue raises this and defers to planning. Decision 3.
5. **427.** Mislabeled but public (C9). Decisions 4 and 9.
6. **Release type.** Decision 5 conflicts with AGENTS.md 2.2 as written (exception recorded in Decision 10). AGENTS.md also states `Current version: **1.3.6**` (`AGENTS.md:55`) and uses 1.3.6 in the release examples; `package.json` is 1.4.2.
7. **Tests that call `response(n)` directly and expect 500 for a code that will change.** Searched `test/` for 201, 202, 204, 409, 422, 429, 503 near `response(` and for `Internal Server Error` expectations. The matches are `ApiRequest.format()` tests (`test/response/response-format-unit-tests.jest.mjs`), unrelated to templates, two fixtures with their own bodies (`test/cache/force-refresh/integration/force-refresh-integration-tests.jest.mjs:263`, `test/config/performance/appconfig-async-init-performance-tests.jest.mjs:291`), and the per-format `response(999)` tests. Nothing else relies on a changing code falling back to 500. Class-fallback tests for unlisted 2xx and 4xx codes are new.
8. **Docs that name the supported codes.** `CHANGELOG.md:407` ("Added responses for 408, 418, and 427") is the only list. No user documentation lists the codes, so the new documentation introduces the table and the fallback rule.
9. **`createGenericResponseModule` JSDoc `@returns`** lists each member by name (`generic.response.js:39`) and must be updated. The documentation tests skip `generic.response*` files (`test/documentation/property/jsdoc-*-tests.jest.mjs:98,115`), so nothing flags a stale list.
10. **RFC 9110 content rules.** 204 and 304 cannot contain content and 205 must not (sections 15.3.5, 15.3.6, 15.4.5, verified against rfc-editor.org on 2026-11-13). 301, 302, 303, 307 and 308 "usually" carry a short note, which is not a requirement (section 15.4). Decision 8 relies on this.

## 6. Proposed approach

Every part below follows a locked decision.

1. **`src/lib/tools/generic.response.js`.**
   - Add to `STATUS_CODE_MAP`, with RFC 9110 and IANA names: 201 "Created", 202 "Accepted", 204 "No Content", 409 "Conflict", 422 "Unprocessable Content" (the current IANA name for 422), 429 "Too Many Requests", 503 "Service Unavailable". Keep 427 as is (Decision 4).
   - Add a private constant listing the codes with no body (204). For those, the factory sets `body: null` and does not call the formatter. The `response204` object is also the fallback for statuses that carry no content (Decision 8).
   - Change `response()` to: parse the code; return `this["response" + code]` when present; otherwise return `this.response200` for 200-299, `this.response400` for 400-499, `this.response500` for 500-599; for 100-199, 300-399 and 205 return `this.response204` (no body); for anything else (NaN, below 100, 600 and above) return `this.response500`.
   - When `response()` resolves 427, call `DebugAndLog.warn` once per container (a module-level flag in `generic.response.js`) with a message in the style of `DebugAndLog.class.js:138`, for example `response427 is deprecated: 427 is not a registered HTTP status. Use response429.` `response()` still returns the 427 template. `generic.response.js` requires `./DebugAndLog.class`; there is no require cycle (Decision 9).
   - Update the JSDoc: `@returns` member list, the class fallback rule, and an example for an unlisted code.
2. **`generic.response.xml.js` and `generic.response.rss.js`.** Replace `statusCode === 200` with `statusCode >= 200 && statusCode < 300` for the `<hello>` branch. JSON, text and HTML modules need no change.
3. **`Response.class.js` `reset()`.** After `this.set(newObj, contentType)`, assign `this._body = null` when `newObj.body === null`. Update the `reset()` JSDoc: a `null` template body clears the body, and a template is chosen by `response(statusCode)` including the class fallback.
4. **Types.** In `types/lib/tools/index.d.ts` add `response201`, `response202`, `response204`, `response409`, `response422`, `response429`, `response503` to `GenericResponseModule`; add `@deprecated` with "use response429" to `response427`; rewrite the `response()` description for the class fallback. Add a read of one new member and of `response429` to `test/types/consumer-tools.ts`.
5. **Documentation.**
   - `docs/01-advanced-implementation-for-web-service/response-management.md`: a "Generic response templates" section with the table of codes and messages, the class fallback rule (including that 1xx, 3xx and 205 have no body, with a redirect example that passes `headers: { Location }`) and an example of customizing `response400` to change every unlisted 4xx, that `response(n).statusCode` of a fallback is the template's, how to add `response<code>` through `Response.init()`, how a 204 behaves (no body; API Gateway removes it; only REST API was checked, and that the `null` body on 3xx and 205 was not checked behind any integration; pointer to the cache-header guidance), and that 427 is not a registered status and `response429` replaces it.
   - `docs/features/tools/README.md`: rewrite "Generic Response Generators" so it matches the real API (module objects with `response(n)`, `responseNNN`, `json()`, `html()` and so on). (I1)
   - `docs/cloudfront-notes/lambda-proxy-response-body.md` is not changed (Decision 6).
6. **CHANGELOG.** Create `## v1.4.2 (unreleased)` above `v1.4.1`. Added: the seven templates and `response429`. Changed: the fallback by class for unlisted statuses (with the old and new bodies), a custom `response500` no longer applying to unlisted 2xx and 4xx statuses, `reset()` clearing the body when the template body is `null`. Deprecated: `response427`, with migration to `response429` and a one-time `warn` log line when `response()` resolves 427. Changed also lists that 1xx, 3xx and 205 now return no body. Existing dated sections are not edited, no release date or intro is written, and entries use the form `- **Title** - Description.` in the category order Fixed, Added, Changed, Deprecated (steering `changelog-convention-package.md`, which replaced `changelog-convention.md`). The heading is created in the final task of `tasks.md`, not before. Link `#252` option 3 as the origin and state in the entry that the change ships as a PATCH and that this is an exception to AGENTS.md 2.2 (Decisions 5 and 10).
7. **Tests** (Jest, `*.jest.mjs`, no `seed` option on `fc.assert`).
   - Update `generic-response-module-tests.jest.mjs` and `generic-response-module-property-tests.jest.mjs`: the known list, the message table, the count in the test title, `EXPECTED_OUTPUTS` per format. Replace Property 3 with one property per class (unlisted 200-299 except 205 to `response200`, 400-499 to `response400`, 500-599 to `response500`), one for 100-199, 300-399 and 205 (identity with `response204`, `body` is `null`), and one for out-of-range input (identity with `response500`). Generators are built from the range with the known list filtered out.
   - Add per-format tests for each new code in the five `generic-response-*-tests.jest.mjs` files, including the XML and RSS `<hello>` form for 2xx and the HTML title.

   - Run `npm test`, `npm test -- test/documentation/`, and `npm run lint` on the touched files. `npm run lint:ci` fails on the repository baseline, so judge lint by the files this change touches. Check the process count while property tests run (steering `test-execution-monitoring.md`).

**Alternatives considered**
| Alternative | Why not chosen |
|-------------|----------------|
| Documentation only: state that ten codes have templates | Leaves `201 {"message":"Internal Server Error"}` as the default for the most common success codes and does not help #252 |
| Keep the single 500 fallback and add templates only | Considered in Q2 option A; not chosen (Decision 2). Leaves 410, 413, 415 and every other 4xx with a 500 body |

## 8. Risks and mitigations

| Risk | Mitigation |
|------|------------|
| An application that read `response(n)` for a status that now resolves to a different template sees different output | Listed under Changed in the CHANGELOG with old and new bodies. The old output was a defect; no test in this repository relies on it (gap 7) |
| An application with a customized `response500` loses that body on unlisted 2xx and 4xx statuses (N1) | State it in the CHANGELOG and docs. The application can customize `response400` or `response200`, or add `response<code>`, which wins over any built-in |
| A 410 is sent with the body "Bad Request" (class representative) | Documented. The application customizes `response400` or adds `response410` through `Response.init()` |
| Shipping changed default output and new exports as a PATCH contradicts AGENTS.md 2.2 | Decision 5, the precedent of 1.4.1, and an explicit statement in the CHANGELOG naming the exception (Decision 10). AGENTS.md is not edited, so its rule and this release differ until someone updates it |
| Every added code is permanent public surface (`responseNNN` plus type members) | The list is limited to seven codes with IANA names (Decision 1) |
| `reset()` change clears a body where a custom `null`-body template used to keep the old one | The previous behavior was accidental (C6). CHANGELOG Changed. Limited to a resolved body of exactly `null` |
| New required members on `GenericResponseModule` break a consumer that hand-builds a typed object | Unlikely, because the modules are consumed, not implemented. Mention it in the CHANGELOG |
| A 204 `body: null` behaves differently behind HTTP API, ALB or a function URL | Same shape as `setBodyToNull()`; the documentation says only REST API was checked (Decision 6) |
| A fallback `response(n).statusCode` differs from `n` and a caller reads it | Documented in the JSDoc and docs. It matches today's behavior, where it is 500 |
| Deprecation of `response427` cannot warn on a property read | The warning comes from `response()` (Decision 9). Direct reads of `response427` do not warn; the type's `@deprecated` and the docs cover them |
| Status list drifts between source, types and tests | I4 drift guard |
| 1xx, 3xx and 205 now send no body; a `null` body on 3xx and 205 is unverified behind API Gateway, HTTP API, ALB, function URL and CloudFront | Decision 6: documented as unverified. A caller who wants a redirect body passes one to `reset()` or `setBody()` |
| An application that overrides `response204` with a body changes what 1xx, 3xx and 205 send | Documented in the JSDoc and docs |
| `generic.response.js` gains a dependency on `DebugAndLog` | No require cycle (checked); `DebugAndLog.class.js:138` is a precedent for deprecation messages through `warn` |

## 9. Locked decisions

|---|----------|-----------|
| 1 | Add templates for 201, 202, 204, 409, 422, 429 and 503 (Q1 option B). No 3xx templates. | Each has a body and needs no header the factory cannot supply. 3xx needs a caller-set `Location`, and 304 was not checked at runtime. Can be added later without a break |
