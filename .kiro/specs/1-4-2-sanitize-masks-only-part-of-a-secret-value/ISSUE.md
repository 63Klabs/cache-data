# sanitize() masks only part of a secret value that contains a character outside its pattern

Found while planning [1-4-1-clientrequest-report-whether-a-request-came](../1-4-1-clientrequest-report-whether-a-request-came/PLAN.md) (finding C4, spin-off F1, confirmed as Decision 8). Checked against `main` at `386c2f9` on 2026-11-10 by running `sanitize()` locally. Not checked on a deployed function.

## Summary

`sanitize()` in `src/lib/tools/utils.js` is meant to mask the value of any object key or query-string parameter whose name contains `key`, `secret`, or `token`, and of `Authorization` headers. The pattern that finds the value accepts only the characters `a-z 0-9 + _ : . - /` (case-insensitive). When a value contains any other character, such as `=`, `!`, `#`, `$`, `%`, `@`, or `"`, the match stops at that character. The part before it is masked and the part after it is printed unchanged. For a value that is entirely inside the pattern, the last four characters are printed (up to 25% of the value, at most six), which is the documented behavior.

Passwords and tokens generated by Secrets Manager with punctuation enabled (the default for `GenerateSecretString`), base64 values with `=` padding, and values containing `@` therefore reach the logs almost whole. `DebugAndLog.debug()`, `info()`, and the other level methods pass objects through `sanitize()` before printing them, so the documented "extra layer of protection" does not hold for these values.

## How it happens

`utils.js` line 130 builds `regex1`. Its value group is `([a-z0-9+_:\.\-\/]{1,1024})`. The group ends at the first character it does not allow. `obfuscate()` (lines 58 to 71) then masks only what the group captured and keeps the last few characters of that captured part, and the rest of the original string stays in place.

Local reproduction from the repository root (Node.js 22 or later):

```bash
node -e 'const {sanitize}=require("./src/lib/tools/utils.js"); console.log(JSON.stringify(sanitize({token:"abc!defghijklmnop0123456789"})));'
```

Observed on 2026-11-10 (documentation-style values, not real secrets):

| Key and value | Result | What leaks |
|---------------|--------|------------|
| `secret: "abcdefghijklmnopqrstuvwxyz0123456789"` | `******6789` | The last 4 characters (documented behavior) |
| `token: "abcdefghijklmnop0123456789=="` | `******6789==` | The last 4 characters and the padding |
| `apiKey: "QUJDREVGR0hJSktMTU5PUFFSU1RVVldYWVo0NTY3ODk="` | `******3ODk=` | The last 4 characters and the padding |
| `token: "abc!defghijklmnop0123456789"` | `*********c!defghijklmnop0123456789` | Everything after the first `!`, and one character before it |
| `clientSecret: "user@example.com-abcdefghijklmnopqrstuvwxyz"` | `*********r@example.com-abcdefghijklmnopqrstuvwxyz` | Everything after the first `@` |
| header `x-atlantis-origin-secret: "Abcdefghij!klmnop#qrstuvwxyz$0123456789AB%CDEFGH"` | `*******hij!klmnop#qrstuvwxyz$0123456789AB%CDEFGH` | Everything after the first `!` |

The `Authorization` branch of the pattern behaves differently: `Bearer abcdefghij.klmnop=qrstuvwxyz` gives `Bearer ******wxyz`, because that branch matches up to the closing quote.

## Impact

Any application that logs an object containing such a value at a debug level, in a non-production or a production stage that has debug logging turned on, writes the value into CloudWatch Logs. Reading those logs is a smaller privilege than reading the secret. The documentation already tells users not to rely on `sanitize()` ("best effort", "avoid logging sensitive data"), so this is a defect in a last-resort control, not a primary leak. The finding came from the ingress secret in spec `1-4-1-clientrequest-report-whether-a-request-came`; the Atlantis platform generates that secret without punctuation, so the secret there shows only its last four characters.

## What was verified

- The five probes above, run locally on 2026-11-10 against `main` at `386c2f9`.
- The existing tests that pin current behavior: `test/utils/sanitize-obfuscate-tests.jest.mjs` expects, for example, `********56`, `apiKey=******8E1D` inside a URL, and `Digest ******8f0e`.

Not verified:

- Whether any consumer relies on the partial output.
- The behavior of values that span a JSON escape (`\"`, `\\`) in the Authorization branch.
- Timing on adversarial input after any change to the pattern (the pattern is bounded to avoid catastrophic backtracking today, and a new pattern must keep that).

## Expected behavior

A value that follows a `key`, `secret`, or `token` label is masked in full, whatever characters it contains, up to the end of the JSON string value or the end of the query-string parameter. Values made only of the currently allowed characters keep today's output (the last few characters, at most 25% of the value and at most six), so the existing tests keep passing.

## Possible fix

- Change the value group in `regex1` from a character allowlist to "everything up to the closing quote, `&`, whitespace, or end of string", with an explicit upper bound as today, and keep `obfuscate()` unchanged.
- Add unit tests for the table above and property tests for "no character after the label's value start survives", with generators that are safe by construction (see `.kiro/steering/test-execution-monitoring.md`).
- Update `docs/features/tools/README.md` (sections "Sanitize and Obfuscate functions" and "sanitize() Function") if the stated limits change.

## Open points for planning

- Whether to keep printing the last four characters at all, or to mask short secrets completely.
- Whether the Authorization branch and the key branch should share one value rule.
- Whether to treat a quoted JSON value and a bare `key=value` pair differently.
- Whether the change needs a CHANGELOG "Security" entry or a "Fixed" entry.
